# Gate 4.7 C2 approval security design — proposed, not yet approved

## 1. Goal and trust boundary

A sensitive action must not execute unless the trusted approval host displayed the complete, canonical request, received a human approval for that same request, and the trusted execution broker atomically consumed a fresh grant for exactly those arguments. A model, tool response, remote content, or other untrusted input may *request* an action but cannot approve one, issue a grant, alter the approved bytes, or directly reach an actuator. Failure, uncertainty, unsupported arguments or unavailable infrastructure means denial.

**Trusted:** the broker, its executor/dispatch adapters, trusted approval UI and host OS/compositor/session configuration; the human is the approver. Broker/UI binaries and configuration must be installed and updated through an independently trusted administrative channel. **Untrusted:** model output, task descriptions, retrieved content and data from tools, and any separately isolated planner/worker process. Request strings never become trusted UI instructions.

**Boundary requirement:** broker-owned, OS-protected execution is essential. Move or wrap every release-in-scope sensitive actuator so that only a trusted broker/executor can invoke it, and confine any adversarial worker so it cannot directly use the filesystem, IPC, portal, AT-SPI, input devices, network, or other actuator with equivalent authority. A check that returns a boolean to an untrusted caller which then invokes an actuator is *not* this boundary. The current island UI, router, and executor can share a process; all code in that process is trusted, and no Python `frozen` class, private member, MAC key in that process, UID comparison or in-process callback defends against compromised code there. `SO_PEERCRED` distinguishes UIDs, not processes of the same UID. A root, administrator, compromised broker/UI/compositor, attacker with equivalent desktop/input rights, or malicious same-trust-domain code is outside this boundary; enforce stronger isolation before making any stronger claim. Surface refusal is defence in depth, not a solution for a compromised desktop.

The current repository does not establish this deployment boundary. If it cannot be built and independently verified on the target host, affected sensitive actions must remain disabled/fail closed; this is not production-ready merely because unit tests pass. GUI screenshots cannot prove that a human actually read or understood a request.

## 2. Canonical request and exact display

- The trusted executor validates each tool against its schema and computes the **final** arguments and any resolved action identity before requesting approval. Reject unknown fields, duplicate object keys, unsupported types, non-finite floats and non-canonical inputs; never silently coerce unexpected objects with `str()`.
- Define a versioned canonical UTF-8 JSON encoding with deterministic key ordering, explicit allowed primitive types, stable escaping and no ambiguous numeric forms. Freeze its bytes at request creation. The execution-binding payload includes protocol version, tool identifier, exact final arguments, target identity, risk and relevant scope. Broker-generated random request ID, session identity and monotonic deadline are bound in the grant; title and warnings cannot redefine or omit the payload.
- The trusted UI receives those exact bytes on its authenticated private broker channel, verifies the full SHA-256 itself, and displays a lossless, escaped representation of the *entire* payload and the full hash; controls/bidirectional formatting characters are made explicit. No silent ellipsization/truncation of security-relevant information. Use a scrollable accessible view, clear indication of all content and explicit acknowledgement after review; do not claim that viewing proves comprehension. If content cannot be displayed completely within strict resource limits, deny rather than approve a preview. Do not display secrets by accident: deny unsupported secret-bearing approval flows until a separately designed secure reference/confirmation flow exists.
- UI approval responses carry `{request_id, payload_hash, decision}` on the dedicated authenticated channel. The broker compares both ID and full hash against its frozen request; stale, mismatched or malformed responses are refused. UI never accepts a planner-supplied boolean callback as evidence of human approval.

## 3. Grants, concurrency and execution

- Broker creates unpredictable, opaque grant handles only *after* a matching approved response. The broker keeps authoritative immutable payload/hash, request ID, session/principal, expiry and state in a private store; a handle is not valid just because a caller constructs an object with matching attributes. One-use, bounded monotonic lifetime; no caller-controlled expiry or reset. Memory-only state is invalidated on broker restart; no replay across sessions. If handles leave the broker, only authenticated OS channels and random capabilities with enough entropy are acceptable; secrecy alone does not replace channel isolation or authorization.
- Serialize pending prompts or keep a bounded, locked per-request state machine: `PENDING → APPROVED → CONSUMED`, or `DENIED/EXPIRED/CANCELLED`; bind queued UI callbacks to their own request ID. Deny concurrent overflow, timeout, close, cancellation, stale callback, duplicate response, malformed response and UI/broker disconnection. Never let an old callback resolve a newer request.
- At dispatch, atomically verify the frozen canonical payload, principal/session, policy, target and deadline and transition the grant to consumed **inside the broker**. Dispatch the exact validated immutable broker-owned arguments, not a mutable copy returned to the requester. Deny divergence, altered targets, forged handles and replay. Consume before the operation; failure or crash never reactivates it. At-most-once grant use does not by itself prove that an external actuator executed exactly once.
- Recheck target identity and safety immediately before physical dispatch; GUI races/overlap require compositor-specific mechanisms and remain host-verification issues. If reliable identity or confinement is unavailable, deny. A separately checked AT-SPI label followed by a new label/occurrence match is not node identity.
- Remove `computer_use.py`'s `approved_child` auto-approval; every sensitive child action obtains a real individual grant. Audit other paths including `ApprovalEngine` and `skills.py`'s auto-callback, as well as all `request_bound_approval`/`verify_and_consume` callers, for equivalent bypasses. No permissive legacy boolean adapter in production. Migrate each release-in-scope action to the broker-owned dispatch or disable it; preserve old public APIs only if they cannot lead to unmediated execution. This requires changes beyond the three named files and controlled deployment setup; a small in-process patch alone does not satisfy this design.

## 4. Island Unix socket — separate from approval transport

The existing socket is a command endpoint, not a GUI surface and not an approval-decision channel. Bind under the per-user `XDG_RUNTIME_DIR` only after validating a real, correctly owned private runtime directory; avoid following symlinks, reject unsafe ownership/mode and ambiguous or live existing endpoints, and use an owner-only socket with restrictive creation permissions. Do not blindly unlink an existing path; coordinate single-instance ownership and only remove the exact socket inode created by this server.

For every accepted connection, obtain Linux `SO_PEERCRED` before reading any request and require the expected session UID; reject failures and other UIDs, set read deadlines, strictly frame and bound messages, decode strictly, and allow only documented non-approval commands. No command on this endpoint may approve, issue grants, or send broker UI decisions. UID checks and mode 0600 block other UIDs, **not** other processes under the same UID; if same-UID peers are outside the intended trust domain, disable sensitive commands on this endpoint or use a separately established authenticated channel and OS isolation. Never infer human consent from `ask`, `toggle`, `auth-*`, or `quit`.

The UI–broker approval channel is a separate inherited private socketpair or equivalently protected authenticated endpoint established by the trusted launcher, not this publicly discoverable per-user command socket. Authenticate the peer/channel and session, check PID/UID as supplementary evidence, and reject unknown endpoints; merely trusting a claimed PID or UID is insufficient against an actor in the same trust domain.

## 5. Verification and rollout gates

- Offline tests use injected trusted broker/executor interfaces and no real input or fake GTK rendering: malformed/duplicate/non-canonical payloads, long warnings and payloads, distinct Unicode forms, displayed-byte/hash mismatch, unknown handles, direct token construction, mutation, replay, expiry, concurrent approvals, delayed/stale UI responses, cancellation, restart, caller substitution, exact executed args, child auto-approval and refusal to dispatch when infrastructure is unavailable. Assert the action adapter was not invoked on every denial.
- Dedicated IPC tests use temporary Unix sockets and controlled peer credentials; wrong UID/credential retrieval failure, malformed or oversized messages, unsafe paths, ownership and stale/live endpoint handling must fail closed. Mocks test logic only, not actual isolation.
- Host-only tests use a real trusted session/compositor and isolated test actuators, verify full accessible display and matching decision, multiple prompts and cancellation, target/overlap changes, unauthorized peers and isolation against an untrusted worker. Validate absence of alternative actuator paths; no destructive SystemWiper operation is executed. Passing tests are scoped evidence, not proof against a compromised host.
- Review all sensitive entry points and backends before enabling them; unsupported paths fail closed. Keep the signed-manifest verifier's no-key failure and other release gates unchanged. Preserve old checkout, tags and prior audit evidence.

## 6. Outstanding decisions before implementation

1. **Boundary and deployment scope:** approve the separately protected broker/executor and isolated worker design, including disabling sensitive actions when the boundary cannot be established. The current same-process architecture cannot simultaneously support arbitrary hostile in-process code and guarantee unforgeable approvals.
2. **Protected manifest sequencing:** `selfimprove/protected_hashes.json` currently has exactly six core hashes and is itself separately protected. Prompt 3's authorized change to `approval.py` will invalidate its existing hash. Prompt 10 asks to update the protected manifest, but the sequence also requires Prompt 3 to pass and commit cleanly. An explicit authorization is needed to update **only the approval.py hash** in that six-entry manifest in the same Prompt 3 commit, or else leave it intentionally mismatched and accept that integrity checks cannot pass until Prompt 10. A self-hash must not be added to the same manifest. All other protected files and manifest entries remain unchanged absent further authorization.
3. **Release readiness dependencies:** real host isolation, trusted display behavior and operator-provisioned trust materials are not available in this sandbox. A Prompt 3 implementation without these properties must remain marked incomplete, not be described as a finished security boundary.
